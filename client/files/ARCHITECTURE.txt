Syncthing integration findings - 2026-10-22

Implemented: an optional background file-preparation companion. Syncthing moves
immutable objects and saved snapshots; flim continues ordering live edits.
The companion never opens a project, pairs a device, changes daemon settings,
or starts a service. See README.txt for publish/prepare/watch commands.

    Saved FLP + standard sample paths
             |
          publish -> content-addressed objects + snapshot manifest
                                  |
                         Syncthing shared folder
                                  |
                       prepare/watch verifies all hashes
                                  |
                     native sample cache + private local FLP
                                  |
                     manual Open in matching FL Studio

Architecture evidence

Source reviewed: official syncthing/syncthing tag v2.1.7, commit
d6d0181f7d466381c4b39ec8fd944c364f939b32. Links below are immutable.
Base: https://github.com/syncthing/syncthing/blob/d6d0181f7d466381c4b39ec8fd944c364f939b32/

1. Watchers, debounced scans and block hashing support background file transfer.
   The copier/puller/finisher pipeline reuses verified blocks and fetches missing
   blocks. This suits saved snapshots and samples. It supplies no FL edit locks,
   transport timing or semantic project merging.
   lib/model/folder.go:233,1089; lib/model/folder_sendrecv.go:247,1209,1443,1572;
   lib/scanner/blocks.go:34; lib/config/folderconfiguration.go:57.
   https://docs.syncthing.net/users/syncing.html

2. Version vectors detect concurrent versions. Conflicts preserve a separate
   .sync-conflict-* file; they cannot combine two FLP arrangements. Digest-named
   immutable snapshots avoid competing writes to a single active project.
   lib/protocol/vector.go:212,251; lib/model/folder_sendrecv.go:1722,1920,2277.
   https://docs.syncthing.net/users/syncing.html#conflicting-changes

3. Completion is per file, with temporary files, close/sync and RenameOrCopy.
   Windows target preparation and fallback copying prevent a universal atomic
   replacement guarantee. A project and its samples are not one transaction.
   lib/model/sharedpullerstate.go:321; lib/model/folder_sendrecv.go:1705,1759;
   lib/osutil/osutil.go:27,91.

4. REST completion is approximate aggregate progress. Downloaded blocks can
   count before final installation; 100% does not prove a project ready to open.
   A successful POST /rest/db/scan confirms a local scan, not remote delivery.
   The companion therefore depends on local verified file contents, requiring
   no Syncthing API key and remaining independent of a daemon version's API.
   lib/model/model.go:914; lib/api/api.go:764,1542.
   https://docs.syncthing.net/rest/db-completion-get.html

5. Scope each share to a project/session. Keep active FLPs, prepared projects,
   autosaves and caches outside it; ignore /.flim-staging on each device.
   .stignore is local and is not synced. Versioning archives remote changes,
   and does not provide history for every local save. No core Windows file
   placeholder/hydration API was found in the bounded source/API review.
   https://docs.syncthing.net/users/ignoring.html
   https://docs.syncthing.net/users/versioning.html

Practical limits

No speedup, audio-dropout improvement, large-library performance, interrupted
block-resume, disk-full behavior or cross-NAT performance was measured. Real
peer tests with friends remain necessary. This does not merge FLPs or allow
mixed FL25/26 sessions. Automatic dependency discovery/rewrite covers standard
event196 paths; opaque/plugin-compressed state may require explicit assets and
manual relinking. The live project.load protocol still sends project snapshots
through flim's relay. Syncthing supplements preparation and cache reuse.

The existing relay source targets Fly.io, with a Cloudflare Tunnel deployment
guide. No server or tunnel was deployed. Syncthing's peer transport is a separate
path; keep its admin API local. The companion works through a chosen folder,
without copying Syncthing implementation or redistributing its executable.
Syncthing itself is MPL-2.0; any future daemon redistribution must retain notices
and corresponding source availability.
